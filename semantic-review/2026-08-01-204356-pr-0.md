# Phase 3 domain foundations without a connected product runtime

The three Phase 3 commits add domain libraries, database tables, static status pages, a scanner endpoint, and optional worker/MCP shells while preserving the Phase 2 submission tests. The local acceptance test composes libraries directly with mocks, so it does not prove that web, ingest, worker, scanner, and MCP form one workflow. The scanner’s documented rebinding guarantee is false because validated DNS answers are not pinned to the connection, and several isolation, evidence, and privacy claims exceed the implementation. Browser/PDF/official-provider omissions are honestly documented sandbox limits; the blockers below are separate defects or acceptance overclaims.

**Watch for:** **confirmed P1** scanner SSRF through unpinned DNS; **confirmed P1** Phase 3 product routes and jobs are mostly demo/test-only; **confirmed P1 for any production launch** there is no Phase 3 PostgreSQL runtime adapter and the web control plane refuses production. **Confirmed P2** gaps remain in form-scoped MCP authorization, relational tenant integrity, code-analysis evidence, captured-local delivery, report provenance, analytics IP filtering, and routing bounds.

**Verdict**: NEEDS_CHANGES

## High-level view

Phase 2 ingest and worker behavior remains operational, but submissions do not trigger Phase 3 routing, analytics, drift, monitoring, reliability, integration, or report work. The scanner is the only genuine Phase 3 HTTP operation; web routes are static cards, the default worker has no Phase 3 queue/handlers, and the MCP executable exits without listening.

The scanner validates DNS before each hop, then gives the hostname to global `fetch` for an independent lookup. Its test catches a redirect that explicitly resolves private, not a same-host answer change between validation and socket connection.

Persistence stops at DDL and local/in-memory services. Phase 2 submissions have a PostgreSQL adapter; Phase 3 does not, and the authenticated web repository refuses production. This is compatible with the documented development preview, but not with the claim that PostgreSQL is the production Phase 3 adapter.

MCP excludes real-submission tools and gates synthetic submission behind a dedicated scope, confirmation, and idempotency. Form grants are not applied to workspace-wide tools, so a token restricted to one form can enumerate every form in its workspace once MCP is wired.

Other deterministic outputs are presented with stronger semantics than they establish: regex analysis promotes comments and strings to facts, captured-local integrations discard payloads, reports trust unverified evidence IDs and keep manifests in memory, analytics accepts raw IPv6, and routing does not validate the complete runtime AST.

## Scanner validation is not socket-level IP pinning

**Confirmed P1.** `packages/scanner/src/index.ts:90-91` calls `validateNetworkUrl(current.href, resolver)`, discards its returned `addresses`, then calls `fetcher(current)` with the hostname. Global fetch resolves again, allowing an attacker-controlled name to return public during validation and loopback, metadata, or private during connection. Redirect revalidation does not close this same-hop time-of-check/time-of-use window.

The “rejects rebinding” test in `packages/scanner/src/index.test.ts:24-35` instead redirects to a second hostname whose injected resolver immediately returns `127.0.0.1`; injected fetch never performs DNS. The automated-gate claim in `docs/phase-3-acceptance.md:9` is therefore false. Replace global fetch with a dispatcher whose lookup selects only approved addresses, preserves hostname certificate verification, and checks the connected peer; repeat per redirect and test changing answers with a real local server/resolver.

## Phase 3 composition stops at static pages and optional seams

**Confirmed P1.** The scanner’s `POST /v1/scans` is real, but uses caller-supplied form configuration and persists no tenant scan run. The rest of the topology is disconnected:

```text
Phase 2: web/form -> ingest -> durable submission queue -> worker       (wired)
Phase 3: static web cards    domain libraries    optional worker seams  (disconnected)
                         \-> direct mocked E2E composition only
```

Dedicated pages such as `apps/web/src/app/app/scanner/page.tsx`, `analytics/page.tsx`, `routing/page.tsx`, and `reports/page.tsx` pass hard-coded copy and `status="ready_local"`; `apps/web/src/components/Phase3FeaturePage.tsx:29-30` renders a generic capture claim without a session, workspace, repository, or evidence query. `apps/worker/src/index.ts:375-381` returns without an injected Phase 3 queue and skips queues without injected handlers, while `defaultWorkerDependencies` at line 436 supplies neither. `apps/mcp/src/index.ts:91-93` exports a server factory but has no dependency bootstrap or `listen`; executing it exits immediately. Web and worker also lack dependencies needed to construct these domain workflows.

`packages/testing/src/phase3.e2e.test.ts` calls libraries directly with in-memory objects and mocks; it never drives a request through the service topology. Replace ready labels with unavailable, or add authenticated routes, scan persistence, ingest enqueue hooks, default worker handlers, MCP bootstrap, and a process-level test that drives a real submission across services.

## PostgreSQL is schema-only for Phase 3

**Confirmed P1 for production; documented limitation for the local preview.** `LocalPhase3Store` is constructed only in `packages/phase3-store/src/index.test.ts`; there is no PostgreSQL implementation of `Phase3Repository`, Phase 3 queue, scoped-token repository, analytics store, report repository, or agency repository. `packages/database/src/schema.ts` defines tables no runtime reads or writes. `apps/web/src/lib/repository.ts:20-23` always creates `LocalDevelopmentRepository`, whose guard at `packages/database/src/index.ts:181-194` throws in production; only submission storage selects PostgreSQL at `apps/web/src/lib/repository.ts:47-53`.

The preview/terms honestly label local-only operation, and browser/PDF/official providers can remain unavailable. The overclaim is `docs/architecture.md:11`, which calls PostgreSQL the production adapter and describes immutable Phase 3 history as operational. Narrow that statement to DDL preparation or implement transactional repositories/queues/token/report manifests in all bootstraps, then run restart and concurrent-worker tests against PostgreSQL.

## Form grants do not constrain workspace-wide MCP tools

**Confirmed P2.** `ScopedTokenService.authorize` checks `record.formIds` only when the request includes `formId` (`packages/security/src/index.ts:236-239`). `McpToolService.call` takes that only from arguments (`packages/mcp-tools/src/index.ts:91-99`); `list_forms` returns `repository.listForms(input.workspaceId)` unfiltered at lines 107-108. A reproduction with a token granted only `f1` returned both `f1` and `f2`. Workspace-wide health/reliability and form-restricted creation have the same ambiguity.

Current tools do exclude real submission reads, and synthetic submission has the promised dedicated scope. Make authorization return grants, intersect collection results with `formIds`, define empty grants explicitly, and reject workspace-wide/create operations for form-restricted tokens without a separate workspace grant. Add a two-form test.

## Phase 3 foreign keys do not enforce workspace consistency

**Confirmed P2.** New tables independently reference a workspace and tenant-owned parent without proving they match. `scanner_runs` at `packages/database/src/schema.ts:744-759` and `analytics_events` at line 1106 onward can pair workspace A with workspace B’s form. `routing_decisions` at line 1021 onward can pair workspace A with another workspace’s submission/rule version; report artifacts can do the same with requests. PostgreSQL accepts each individually valid foreign key.

This is dormant because production repositories do not exist. Before adding them, add composite uniqueness to parents and composite foreign keys for `(form_id, workspace_id)`, `(submission_id, workspace_id)`, and `(request_id, workspace_id)`. Scope every worker/repository lookup and add cross-workspace insertion tests.

## Heuristic code scanning is labeled as factual analysis

**Confirmed P2 acceptance overclaim.** Script analysis scans raw source with a form regex at `packages/integration-copilot/src/index.ts:224` and state keyword regexes at lines 244-248. Markup in comments/strings becomes a real form and words such as `success` become runtime states. A reproduction containing only a commented form and `const note="success"` returned one form and `success: true` with `supported: true`. Prompts call the output `Observed facts (not hypotheses)` at line 353, matching `apps/web/src/app/app/copilot/page.tsx:10`.

Non-execution and repeatable output remain valid; factual semantic analysis does not. Use HTML and JS/TS/JSX parsers with source ranges, return unsupported for unmodeled syntax, and label remaining lexical heuristics with confidence/provenance. Test comments, strings, templates, malformed syntax, nested JSX, and aliasing.

## `captured_local` providers do not capture deliveries

**Confirmed P2 acceptance overclaim.** `CapturedLocalIntegrationAdapter.deliver` at `packages/integrations/src/index.ts:94-101` ignores delivery ID, payload, and configuration, then returns `captured_local`; connection state is an instance field. This contradicts `Phase3FeaturePage`’s capture/evidence statement and the routing-to-captured-integration flow in `docs/phase-3-acceptance.md:7`.

Inject a tenant-scoped repository and persist an immutable redacted capture keyed by delivery/idempotency ID before returning captured; persist lifecycle state too. Otherwise rename the result to simulated/not-sent and remove capture claims.

## Report checksum does not establish evidence provenance

**Confirmed P2.** `ReportService` trusts caller-supplied evidence IDs/links, copies them at `packages/reports/src/index.ts:94`, and never resolves them against workspace evidence. Its artifact/manifest index is an array at line 73 populated at line 98, so restart makes stored artifacts undiscoverable. The checksum proves generated bytes did not change, not that evidence existed, belonged to the workspace, or supported metrics.

Use the tables at `packages/database/src/schema.ts:1241-1270`: resolve and authorize evidence transactionally, store evidence type/version/hash and a canonical manifest checksum, persist metadata before publication, and derive workspace from authenticated context. Test forged/cross-workspace IDs, evidence mutation, and restart.

## Analytics accepts raw IPv6 despite the privacy contract

**Confirmed P2 acceptance overclaim.** `validateAnalyticsEvent` rejects `@`, bearer strings, and dotted IPv4 at `packages/analytics/src/index.ts:75-92`, but accepts `2001:db8::1`, contradicting `docs/security.md:17` and `apps/web/src/app/app/analytics/page.tsx:7`. Encoded email/IP forms can also bypass substring checks.

Canonicalize typed dimensions and use `node:net.isIP` for IPv4/IPv6 plus URL/host parsing. Prefer server-generated dimensions; test IPv6, bracket/port forms, encoded email, and attribution sources. A durable single-use attribution store remains a production prerequisite rather than a local-preview blocker.

## Routing bounds do not validate the runtime AST or action values

**Confirmed P2.** `validateRoutingRules` limits rule count, depth/nodes, condition strings, and action-array lengths, but `packages/routing/src/index.ts:71-80` never validates each recipient, integration ID, tag, rule ID, priority, condition kind, or operator. Persisted JSON can carry huge action strings, non-finite priorities, or malformed variants that crash evaluation. Type declarations do not validate database/API JSON.

Parse the complete AST with a runtime schema, enum and scalar/list checks, identifier/address validation, per-element/total-byte limits, and finite priority bounds before persistence and defensively in the worker. Add malformed JSON and oversized-action tests.

`pnpm test:phase2` passed 24 tests and `pnpm test:phase3` passed 47 tests. They cover the Phase 2 local path and isolated package behavior, not socket pinning, Phase 3 service composition, PostgreSQL/restart durability, multi-form grants, or cross-tenant SQL integrity.
